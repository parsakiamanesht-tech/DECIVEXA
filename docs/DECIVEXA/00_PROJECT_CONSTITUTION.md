# DECIVEXA Project Constitution

## 1. Identity

**DECIVEXA** is the product brand. **Decision OS** is the underlying architecture and philosophy.

DECIVEXA is not intended to be a conventional productivity application. Its purpose is to become a long-term personal decision, growth, navigation, and life-management system that understands a person, reasons over evidence and context, helps translate vision into action, learns over time, and becomes a trusted reference for personal development and decision-making.

Founder / Owner: **Parsa Kiamanesh — Originator, Founder & Owner of DECIVEXA**.

Material architectural, philosophical, governance, security, or product-direction changes require founder approval.

## 2. Non-Negotiable Principles

1. **Evidence Before Opinion** — claims about the system, implementation, runtime, architecture, or behavior must be grounded in observable evidence.
2. **Architecture Before Accumulation** — features must strengthen the long-term system rather than create disconnected functionality.
3. **DECIVEXA is not merely a productivity app** — the architecture must preserve its identity as a personal operating/navigation system.
4. **User Value over User Input** — minimize repetitive user data entry; the system should derive, remember, and learn wherever safely possible.
5. **Long-term intelligence is a first-class concern** — architecture must support Personal AI Coach, Research Assistant, Growth Navigation Engine, memory, agents, predictive recommendations, and a future Digital Twin without forcing premature implementation.
6. **Human agency remains primary** — AI recommends, reasons, explains, and assists; it must not silently replace user ownership of consequential decisions.
7. **Privacy by Design** — personal data ownership, export/delete capability, selective encryption, least privilege, and privacy-aware architecture are foundational.
8. **Independent verification** — implementation claims must be verifiable through tests, CI, runtime checks, or explicit evidence.
9. **Development Freeze means freeze** — when an architectural freeze is active, new scope is deferred to the Architecture Backlog unless explicitly approved.
10. **Recovery is part of engineering** — recovery baselines, anchors, evidence, and reproducibility must be preserved before risky changes.

## 3. System Philosophy

DECIVEXA should function as a lighthouse for human goals and growth: understand the person and their environment, clarify what matters, navigate toward meaningful outcomes, support daily execution, learn from outcomes, and continuously improve the quality of decisions.

The system should connect:

- identity and values
- vision and mission
- priorities
- goals
- daily execution
- discipline
- health
- money
- learning
- business
- relationships
- review and reflection
- evidence and memory
- AI reasoning and navigation

## 4. Quality Gate

Every material change should be evaluated against six founder-defined criteria:

1. Alignment with the DECIVEXA vision rather than a generic productivity-app direction.
2. Long-term architectural strength for AI assistant, memory, Digital Twin, agents, voice, and predictive recommendations.
3. Improvement opportunities and architectural debt introduced by the change.
4. User input burden versus system value.
5. AI capability: ability to understand, remember, personalize, reason, and support the Personal AI Coach, Research Assistant, and Growth Navigation Engine.
6. Potential for DECIVEXA to become a trusted reference for the user.

## 5. Change Authority

Founder approval is required before material changes to:

- core architecture
- DECIVEXA philosophy or constitution
- module boundaries
- data ownership/privacy principles
- recovery baselines
- security architecture
- major technology-stack direction
- frozen scope

Deferred ideas belong in the Architecture Backlog rather than being lost or silently implemented.

## 6. Truth Hierarchy

When sources conflict, use this order unless a higher-authority explicit decision says otherwise:

1. Verified repository state and runtime evidence.
2. Approved architectural decisions and constitution.
3. Current architecture/state documents.
4. Approved product/vision documents.
5. Architecture backlog and proposals.
6. Conversation memory or informal discussion.

Conversation history is context, not a substitute for repository evidence.

## 7. Definition of Done

A change is not considered complete merely because code was written. Completion requires the appropriate combination of:

- implementation
- tests
- static verification
- runtime verification when required
- CI evidence
- migration evidence where applicable
- documented architectural impact
- recovery/reproducibility preserved

## 8. Current Strategic Direction

The preferred engineering model is:

- **GitHub** — source of truth and repository history.
- **Claude Code** — primary implementation agent when connected to the repository.
- **GitHub Actions** — independent CI and verification layer.
- **Termux** — runtime verification, GitHub CLI, emergency/recovery fallback.
- **Architecture review** — independent reasoning and governance layer.

The existence of an AI implementation agent does not weaken the evidence-before-opinion rule.
